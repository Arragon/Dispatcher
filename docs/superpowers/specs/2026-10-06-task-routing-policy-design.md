# 任务类型识别与模型路由详细设计

日期：2026-10-06。状态：设计建议，尚未实现、尚未进行真实账号验收。

## 1. 目标与依据

在独立的「发布任务」页面，用户选择项目目录和 Agent 账号、输入任务后，
Dispatcher 通过关键词，或关键词与内部模型的语义分析，识别任务类型，
按用户配置的 policy 推荐具体执行模型及思考强度。全局开关控制是否启用；
独立确认开关控制启动前是否需要确认路由结果。

创建任务明确分为两种模式：手动模式由用户选择 harness/账号、模型和思考
强度；自动模式由用户选择 harness/账号，模型及思考强度按 policy 匹配。
自动模式未匹配到适用规则时，提示用户手动指定并阻止启动，不使用账号默认
模型兜底。账号默认仍保留为手动模式中可以主动选用的快捷候选。

成功标准：用户能看懂为什么得到这个选择，能手动覆盖；实际启动使用同一
选择；历史记录能还原任务分类、规则、模型、思考强度及确认依据。

本设计衔接 [账号模型目录、默认模型、任务选择与用量设计](2026-10-04-agent-model-selection-design.md)
及其 [Linear 文档 06](https://linear.app/inhandy/document/06-本地任务发布模型选择与用量估算设计-31a017057a6e)。
该模型目录方案也仍是设计，不能假定接口已实现。
参考讨论：[比较智能投入](chatgpt-conversation://6ac5289d-4e8c-83ec-8ae4-d605cd841146)。
参考讨论中关于工作流、复盘和学习的内容提供长期方向；这里实现启动前的
任务分类和模型选择，不引入完整工作流引擎或自动学习修改 policy。

### 当前仓库事实

- `packages/scheduler/src/index.ts` 已有确定性的 Runner、Provider、Profile
  筛选，检查能力、容量、标签和资源状态；没有按任务文本选择模型及 effort。
- `AgentProfileConfig.settings.model` 是账号模型配置；Controller 的
  `TaskDispatchBody` 和 `AgentAdapter.start` 尚无单次模型及 effort 契约。
- Controller 统一派发入口负责 READY TaskContract、已登记仓库、受管 worktree、
  启动事务、currentRunId 和幂等结果。新增路由必须进入这条链路。
- 内部 `llm-runtime` 已有角色绑定、模型池、健康状态、结构化请求、token
  用量和失败处理。当前角色没有 `task_classifier`；当前响应也没有可靠的
  单次调用执行模型元数据，需要在该边界补齐，不能读一个可变全局状态代替。
- 适配器当前没有统一的思考强度能力目录。是否支持某个原生 effort，必须
  在具体安装版本、账号、模型及执行后端上验证，不能假设所有 Agent 都支持 high。

以上是 2026-10-06 对当前工作区的读取结果，不代表这些设计已交付。

## 2. 方案选择与范围

推荐「确定性 policy + 可选语义分类」：关键词快速给出候选，内部模型补充
自然语言意图识别，policy 保持最终执行选择权。它能理解同义表达和任务目标，
同时允许解释、测试及重放决策。

另外两种方案的取舍：纯关键词最简单，保留为可选模式；让内部模型直接选择
模型、effort 和账号会混合分类与执行权限，难以保证规则优先级和历史可复现，
不作为本版方案。

本版范围：

1. 首个入口为本地发布页；选定项目和 Agent 账号后，在该账号内选择模型。
2. 设置页管理全局开关、确认开关、识别模式、任务类型、项目/全局规则。
3. 执行选择贯穿 Controller → Scheduler → Adapter → Run/session。
4. 任务与运行页展示决策记录、实际参数证据及既有用量/估算信息。

全局开关对接入此路由流程的发布请求统一生效，不因项目或账号分别绕过。
旧 HTTP/Slack/Linear 入口不在此次默默改成自动选模型；它们继续既有行为，
以后接入须明确入口契约。外部 RHIZA 已明确指定模型的请求保持指定选择。
现有内部 LLM 的角色/模型池路由也不受这个开关影响。

本版不自动改选 Agent 账号、Runner 或 harness，不做成本最优搜索、运行中
升级/降级、失败后换模型、Skill 编排或历史表现驱动的规则更新。后续 RHIZA
可以提交明确阶段和执行选择，再复用本设计的选择事实及执行校验边界。

## 3. 开关与默认值

| 设置 | 建议初始值 | 语义 |
| --- | --- | --- |
| 启用任务模型路由 `enabled` | 关闭 | 开启后允许创建任务时选择自动模式；手动模式始终可用 |
| 执行前确认路由结果 `requireConfirmation` | 开启 | 自动模式下必须确认本次最终选择才能启动 |
| 任务识别模式 `classificationMode` | 关键词 | 可选「关键词」或「关键词 + 语义分析」 |
| 语义分析失败处理 `semanticFailureMode` | 停止自动选择 | 可另选「明确显示降级，并使用唯一关键词结果」 |

| 全局路由 | 路由确认 | 发布行为 |
| --- | --- | --- |
| 关闭 | 开启或关闭 | 仅提供手动模式，用户明确选择模型及 effort 后开始，不调用语义分类模型 |
| 开启 | 开启 | 手动模式直接开始；自动模式展示有效匹配结果，用户「确认选择并开始」后启动 |
| 开启 | 关闭 | 手动模式直接开始；自动模式展示有效匹配结果，用户「开始执行」后启动 |

自动模式没有匹配结果时，上述两种确认设置都不能启动，必须提示手动指定。

关闭确认取消的是额外的路由结果确认，不自动提交草稿，不取消开始按钮，也
不绕过 TaskContract、工具授权、资源状态、仓库权限或 ConfigPlan 的确认要求。
歧义、无效模型和陈旧选择仍需处理；这种修正不属于可被关闭的路由确认。

开启/关闭路由和修改确认策略经 ConfigPlan 保存。草稿以服务端当前配置为准：
确认从关闭切为开启后，旧草稿必须补确认；从开启切为关闭不自动启动等待中的
草稿。所有影响决策的变更使旧决策失效，重新显示结果。运行中的任务不改变。

## 4. 发布页与设置页

### 发布流程

保留独立页面，选择项目目录及 harness/账号后，明确显示「手动模式 / 自动
模式」。手动模式由用户选择具体模型及思考强度，输入任务并开始执行；
自动模式由用户输入任务，经关键词/语义识别后按 policy 填入两项执行参数。
新草稿初始为手动模式；全局开关关闭时自动模式不可选，并说明需在设置启用。
自动模式显示关键词初步结果；混合识别需完成语义分析后才得到可提交的结果。

未匹配时保持自动模式，模型/effort 不填账号默认值，显示「未匹配到适用
规则，请手动指定模型和思考强度。」及「切换手动模式」按钮，开始按钮不可用。
用户主动切换后保留项目、harness 和任务文字，明确选择有效参数才能开始。
手动模式可点击「使用账号默认模型」选用该候选，并明确选定 effort；这个
动作属于用户选择，不是未匹配后的自动兜底，也不形成第三种创建模式。

语义分析由「分析路由」或第一次点击开始触发，不在每个按键后调用模型。
第一次点击开始遇到未分析草稿时，仅生成并展示结果，按钮随后变为
「确认选择并开始」或「开始执行」，避免第一次点击在尚未展示选择时就启动。
刷新原生目录不反复调用分类模型；同一草稿和相同分析版本可以复用其结果。
本次已手动指定完整执行选择，或已显式指定任务类型时，不调用语义模型；
分别直接校验执行选择或按指定类型匹配规则。用户仍可主动运行分析供比较。

结果卡至少显示：

- 创建模式及任务类型、来源：手动 / 关键词 / 语义 / 联合判断 / 未匹配。
- 命中关键词或语义依据、采用规则的名称/作用域/版本。
- Agent 账号、具体模型、原生思考强度及读取支持情况。
- 当前 CLI 价格、倍率、优惠及查询时间；缺失字段显示「未提供」。
- 语义失败、规则冲突或原生目录过期的具体状态及处理入口。
- 「手动指定」和「重新分析」；手动覆盖不修改账号默认或规则。

用户选择模型或 effort 即进入「本次手动指定」，两个参数作为一组最终选择
校验。更换模型后必须重新校验 effort，不能把上一模型的 high 偷带给新模型。
返回「自动模式」需要用户主动点击；新分析不能覆盖手动锁定的选择。

修改任务、项目、账号或任务类型后，旧决策及确认失效。保留任务文字；上下文
改变时清除不再适用的模型/effort 绑定，显示新结果，不跨账号沿用同名模型。

### 设置入口

在设置中增加「任务模型路由」区域，包含上述开关和模式、任务类型表、规则
列表与试算。Agent 详情仍负责模型目录及账号默认模型，不复制另一套目录。

任务类型编辑：名称、定义、关键词组。规则编辑：名称、启用状态、项目或全局、
适用账号、任务类型、优先级、目录中的具体模型及该模型支持的 effort。
选择模型、保存相关执行选择时读取原生目录；保存仍受 ConfigPlan revision
和现有活动账号保护约束，不能为了修改规则重建正在运行的 Adapter。

试算输入示例任务，显示分类、匹配/排除原因、胜出规则、模型和 effort。
关键词试算不调用内部模型；用户明确点击语义试算才调用配置的内部模型。
试算不创建任务、worktree 或 Agent 会话。发布页使用服务端已应用的 policy；
未应用配置的试算标为「草稿规则」，结果不可直接用于启动。

## 5. 任务类型与关键词识别

建议预置以下可编辑类型。仅预置类型和例子，不自动绑定未经验证的模型排名。

| 类型 ID | 主要目标 | 关键词例子 |
| --- | --- | --- |
| `documentation` | 文档、说明和注释 | README、文档、说明书 |
| `test_change` | 新增或修订测试 | 单元测试、测试覆盖、回归用例 |
| `bug_fix` | 定位并修复明确故障 | 修复、报错、bug、崩溃 |
| `diagnosis` | 排查原因、分析证据 | 根因、排查、为什么变慢 |
| `ui_implementation` | 页面和交互实现 | 页面、布局、交互、样式 |
| `feature_implementation` | 实现明确功能 | 新增功能、实现接口 |
| `refactor` | 调整内部结构 | 重构、整理模块、拆分组件 |
| `architecture_design` | 边界、架构和设计决策 | 架构、状态事实源、ownership |
| `migration` | 数据、协议或依赖迁移 | 数据迁移、schema 变更、升级依赖 |
| `research` | 调研及方案比较 | 调研、比较方案、选型 |

一个类型具有多个关键词组，组内 `any` 至少命中一项（非空时），`all` 必须
全部命中，`exclude` 任意命中即排除该组；组间是 OR。一个组的 any/all 至少
一项非空，避免空条件匹配所有任务。未命中的类型也可由语义识别选中。
关键词模式下，唯一候选成为最终类型；多个候选要求选择类型，空候选标为
未识别并提示手动指定，阻止启动。不以命中词数量推断任务复杂度或模型强度。

输入范围仅为本次任务标题和用户填写的任务说明。项目/账号是选择上下文，
不是自动读取文件的授权。附件、代码、日志、检索结果和 Agent 输出不隐式
加入分类输入。用户填写内容按数据处理，文字中的「改配置」「忽略规则」
不具有修改 policy 的权限。

关键词匹配使用 Unicode NFKC、大小写归一化和空白归一化；英文单词按边界
匹配，中文按配置短语匹配，不自动扩展同义词。路径不区分大小写的假设不
用于仓库身份；仓库身份由既有路径登记流程解析。保存归一化命中片段及原文
对应范围，便于解释。关键词本身不能可靠理解否定、引用和多重目标，混合
模式用语义识别补充；关键词模式的局限在试算与设置说明中明确展示。

v1 不支持用户输入任意正则、脚本或 shell。关键词组和规则各最多 100 项，
每个关键词最多 128 个 Unicode 字符，每组各列表最多 30 项；超出在配置
校验中明确拒绝，不静默截断。这是初版资源边界，不做复杂规则语言。

## 6. 内部模型语义分类

### 角色、输入与输出

复用 `llm-runtime`，新增角色 `task_classifier`，绑定现有内部模型池；可以
使用默认池，也可为该角色选择专用池。页面显示分类模型与执行模型的区别。
分类模型从内部 LLM 配置选取，执行模型来自已选 Agent 账号的原生目录。

分类请求包含：任务标题/说明、启用任务类型的 ID/名称/定义。请求不含账号
凭据、完整配置、CLI 私有路径、文件内容、价格或候选执行模型，不给工具。
系统提示明确识别实际目标、区分背景/引用/否定语句、避免补造未表达的要求。

输出遵循受校验 JSON 契约：

```typescript
type TaskClassification = {
  status: "matched" | "ambiguous" | "unclassified";
  primaryType: string | null;
  candidates: string[];
  evidence: Array<{ field: "title" | "prompt"; quote: string }>;
  explanation: string;
};
```

`primaryType` 与 candidates 只能来自本次请求的类型枚举；matched 必须有一个
主类型且包含于 candidates；ambiguous 至少两个候选且主类型为空；unclassified
无主类型且候选为空。候选去重，matched/ambiguous 至少提供一个依据片段。
evidence 最多四项，每项引用最多 160 个 Unicode 字符，必须能在指定输入中
找到；explanation 最多 300 个 Unicode 字符，不要求或保存内部思维链。
可以只有一个语义类型而没有字面关键词，例如「把几个按钮和
说明重新排一下，减少误操作」归为 UI 实现。混合任务主目标不清楚时返回 ambiguous。

服务端严格校验，不接受模型返回的新类型、规则 ID、模型名、effort、账号、
授权结论或配置修改。原生结构化输出不支持时，允许文本 JSON 经同一严格
schema 校验；校验失败即分类失败，不从自由文本猜一个结果。
不把模型自报 90% 之类数字当经过校准的可靠概率，不用它决定是否跳过确认。

### 成本、时限与证据

每次明确分析最多一次逻辑调用，允许内部运行时按已配置池进行现有失败
切换，但共享 20 秒总截止时间和取消信号，不叠加无界重试。输出上限建议
700 token；标题/说明合计语义输入上限 16,000 个 Unicode 字符。超出时
明确提示缩短分类说明或使用手动/关键词模式，不静默截断原始任务。

开始分析前无需额外权限弹窗；启用混合模式时设置页说明任务文字会发送给
已配置的内部模型服务。分析按钮和状态显示这一行为。分类 token 用量单独
记录，不能计入执行 harness 的 token 或账户额度。上游未提供时标为未提供。

每次分析保存输入摘要、分类提示模板版本、类型定义版本、实际内部 profile、
模型、调用时间、请求标识（如有）、用量及验证后的输出。内部运行时必须
返回本次调用的来源信息和失败切换轨迹；不使用 activeProfileByRole 的之后
状态推断并发调用的模型。不同端点原始 payload 和秘密不进入路由记录。
失败切换的尝试若上报用量也分别保留；未上报不补零，不声称用量完整。

同一草稿的有效分析可以复用，键包含操作者、草稿身份、原始任务输入、类型
定义、提示模板和内部角色配置版本。相同草稿进行中的重复请求合并，不能
因双击产生两次分类开销。这里只复用语义分析，不复用原生模型/价格的执行前查询。
修改输入或版本则取消旧请求，旧响应不可覆盖新草稿。用户可明确重新分析；
不同结果分别记录，不因重新查询目录而反复生成不同分类。

### 混合结果裁决

| 关键词候选 K | 语义结果 S | 最终任务类型 |
| --- | --- | --- |
| 任意 | 用户在控件中明确指定类型 | 使用用户指定，记录覆盖依据 |
| 空 | matched，单一主类型 | 使用语义主类型 |
| 唯一或多个 | matched，主类型属于 K | 使用该主类型，联合判断 |
| 非空 | matched，主类型不属于 K | 分类冲突，展示两种依据，让用户选类型 |
| 任意 | ambiguous | 展示候选，用户选类型或手动指定模型 |
| 空 | unclassified | 未识别，提示手动指定模型和思考强度，阻止启动 |
| 非空 | unclassified | 判断不一致，用户选类型或手动指定模型 |
| 任意 | 超时/不可用/输出无效 | 按 semanticFailureMode 处理 |

语义失败默认停止自动选择，保留草稿，允许重试或手动指定。只有用户已在
设置中选择「使用唯一关键词结果」且 K 只有一个类型时才能降级；降级原因
显示并写入决策。K 为空或多个时仍不自动猜测。该降级仅替换分类方式，
不允许换一个执行模型来处理账号无权、模型缺失或 effort 不支持。

确认开关关闭时同样按上表裁决；它不把分类歧义转为自动选最贵模型或第一项。
显式指定任务类型是独立控件操作；文本里的 @ 标签不在 v1 新增控制语法。

## 7. Policy 选择与优先级

分类和路由分成两个小数据集：TaskType 定义识别方法；ModelRoutingRule
绑定任务类型与具体执行选择。用户调整模型不用重写分类提示或关键词。

规则字段：稳定 ID、名称、enabled、taskTypeId、repositoryId（空为全局）、
profileId（必填）、priority，以及 `target = { modelSelectionId, reasoning }`。
reasoning 为显式原生值，或明确标为「原生默认」；不是自由文本提示。
模型身份来自同账号、项目上下文的原生目录，不用显示名跨 provider 匹配。

手动模式直接校验用户明确指定的模型和 effort，不用 policy 替换选择。
自动模式的规则优先级只有两层：

1. 已选项目、账号和已识别类型的项目规则。
2. 已选账号和已识别类型的全局规则。

两层均未匹配时返回 `NO_MATCHING_RULE`，提示用户手动指定，不能启动。
不新增「匹配全部任务」的隐式规则，不使用账号默认模型自动兜底。

同作用域按 priority 降序，数字越大越优先。同最高优先级规则若目标完全
相同，可合并依据并稳定排序 ID；目标不同则 RULE_CONFLICT，用户修正规则
或本次手动选择。不能用文件顺序、创建时间、模型价格或 LLM 偏好暗中破平局。
项目规则总是优先于全局规则，优先级数字不跨作用域比较。

不存在适用规则与存在但无效规则要区分：没匹配规则提示手动指定；胜出
规则的模型/effort 无效时停止，不能退到低优先级、全局或默认模型。
分类未识别同样提示手动指定。用户在手动模式明确选用账号默认模型时，
也要校验当前目录及 effort；无效则要求重新选择，不擅自选第一项。

示例配置策略可以是「文档 → 用户选定的经济模型 + 原生 low」，「架构设计
→ 用户选定的推理模型 + 原生 high」。这里没有对特定模型能力排名或倍率的
断言；管理员先从真实账号目录绑定目标，未绑定的示例不能生效。
同一个任务类型可以在两个项目或两个账号绑定不同目标。

TaskContract 的要求、账户资源限制和权限约束始终是硬门槛，不由上述优先级
覆盖。Skill 默认路由和模型能力别名等来自参考讨论的长期方向暂不引入。

### 完整示例

用户在所选项目输入「写一份报告比较数据库升级方案，这次不执行迁移」。
关键词产生 research/migration 两个候选；内部模型识别目标是比较方案，
primaryType 为 research，依据是「写一份报告比较」及「不执行迁移」。联合
裁决采用 research，随后匹配该项目、该账号的 research 规则，得到用户曾
配置的具体模型与原生 effort。页面显示整个选择依据和当前原生费用标签。
确认开启时用户确认并开始；关闭时看见结果后开始即可。最终运行保存该
分类和规则版本，不因以后改成另一个研究模型而改变历史。

若只有 migration 关键词候选、语义给出 research，则显示冲突，用户明确
选择 research 后再匹配规则。若 research 胜出规则中的模型已消失，则停止
启动并要求修正选择，不能因为另一个模型仍存在就替用户切过去。

## 8. 思考强度的原生能力契约

对每个账号/模型/后端，适配器返回明确能力状态：支持显式选择、只支持原生
默认、未提供/未验证。支持选择时提供原生 effort 值、显示名、默认值（如有）、
来源、能力版本和读取时间。low/medium/high 是可能的显示值，不能定义一个
全平台强制枚举；xhigh、max 等只在原生能力确实提供时出现。

运行参数保持原生值和身份，通过已验证的 Adapter 映射为固定 argv 或原生
协议字段。不修改共享账号配置，不给 prompt 添加「请深入思考」冒充 effort。
「原生默认」是明确选择的模式，参数可省略，但不显示为 medium；上游没有
回报实际值时显示「原生默认，实际值未上报」。

能力来自原生模型接口/CLI 信息；原生接口未返回时，可用对应安装版本经过
验证的适配器能力说明，但必须标明来源及未进行实时读取的事实。不能把
适配器说明当实时账号模型、价格或倍率来源。未知能力不得开放显式 effort。

规则保存时验证，启动前再次验证：模型存在、支持单次选择、effort 在当前
能力内、映射可执行、实际工作目录上下文一致。Unsupported/unknown 不自动
降为 low、medium 或省略参数。用户可以明确改选「原生默认」后再启动。

`modelSelection` 记录请求的模型和 effort；原生事件或结果若提供实际执行值，
另记 runtime evidence。二者不混写。若上游明确执行了其他模型/effort，展示
不一致并记录异常；不能声称启动参数就是执行端确认。规则自动选择只支持
原生具体模型条目，不能把上游 auto/档位条目冒充确定的最终模型。

## 9. 决策快照、确认与执行事务

预览先产生服务端决策快照，概念名 `ModelRoutingDecision`，避免与 Scheduler
当前用于选 Runner/Profile 的 `RoutingDecision` 混用。该快照包含：

- decisionId、actorId、草稿/Task 输入 revision 与原始输入身份摘要。
- repositoryId、profileId、Task/contract revision（已有时）及执行上下文身份。
- 配置/类型定义/规则版本，识别模式、候选与证据、语义调用来源。
- selectionMode（manual / policy）、匹配及排除的规则、最终 taskType、选择来源
  和完整模型/effort；未匹配的 needs-input 决策没有可执行目标。
- 原生目录/能力/价格的内容版本及快照、查询时刻。
- requireConfirmation 的服务端值、状态、创建时间和有效期。

输入身份摘要覆盖原始标题、任务说明及显式选择，不能使用大小写/空白归一化
后的关键词文本计算。任务里代码标识符或空白变化也必须使确认失效；分类
匹配的归一化与执行意图身份不是同一个概念。

未提交快照有效期建议 10 分钟；不能用它代替执行前新查询。失效保留原因和
草稿。预览内部状态 pending/ready/needs-input/expired/consumed 不加入 canonical
Task/Run 状态机。用户确认及开始点击记录为决策事件。

自动模式且确认开启时，点击「确认选择并开始」同时提交确认与派发意图；服务端绑定
当前已认证操作者、decisionId、完整最终选择和 input/config revision。
不接受任意 `confirmed: true` 布尔值代替服务端校验。
自动模式且确认关闭时记录 `confirmation.mode = policy-exempt`、有效配置版本及操作者
开始事件，明确未发生额外路由确认；不是伪造 user-confirmed。

手动模式点击「开始执行」提交用户明确选择，记录
`confirmation.mode = explicit-selection`，不额外要求自动路由确认。
手动覆盖自动推荐会明确切换为手动模式，保留覆盖来源；服务端验证完整手动
模型/effort，不能只传 manual 标签而遗漏参数以取得账号默认值。

执行顺序：

```text
校验请求身份、输入和有效决策
  → 校验 TaskContract、仓库及权限
  → 重新读取原生目录、价格及 effort 能力
  → 比较决策的有效选择与配置版本
  → 校验确认条件、资源与容量
  → 按既有工作区管理流程创建受管 worktree
  → 在实际 worktree 上校验有效原生执行上下文
  → 事务保留 STARTING Run、Task/currentRunId、选择事实及派发回执
  → Adapter 使用冻结的模型/effort 启动
```

预览不创建 worktree。只有收到有效开始请求后才允许工作区创建；实际 worktree
的目录/能力/价格查询若与预览不同，启动前返回冲突，已创建工作区按既有
清理/复用策略登记，不直接删除未知或脏目录。内部分类输入不读该目录。

新查询时刻变化但有效内容未变，可以继续；模型身份、可用性、有效价格、
effort 能力或决策相关配置变化返回 `ROUTING_DECISION_STALE`，附新结果，
保留输入，要求重新查看并点击开始。即使确认关闭，也不把页面刚展示的
模型偷偷替换后执行；关闭时刷新后只需开始，不新增路由确认弹窗。
原生查询失败沿用模型设计：旧快照可查看，不能用于启动。

同一 idempotencyKey 的重试返回原派发结果；该 key 绑定操作者、输入及
最终决策意图，不同意图复用返回冲突。保留成功派发时的 decisionId 和 runId
对应关系，已消费决策不能用新 key 再开一个 Run。重试查幂等结果优先于
重新分类和决策过期检查，避免响应丢失后误报过期或重复执行。
确认和派发保留在受控串行/事务边界；竞态下重新检查决策及配置仍有效。
配置应用和启动之间要有 revision 核验与正在启动操作的保护，不能只依赖
网页检查。在创建 worktree 前确认一次，在保留 STARTING 事务内再次检查；
现有活动 Profile 保护维持实际启动期间的绑定，不引入整段模型请求持有数据库锁。

没有自动模型 fallback。启动失败按原错误归类，恢复同一 session 维持原选择；
改模型必须明确发起新的运行并保留新旧证据。租约和 currentRunId 约束保持。

## 10. 模块、契约与接口

复用现有持久化 entity/event、ConfigPlan、llm-runtime 和 Adapter，不引入
新数据库、规则执行框架或模型网关。这个需求的规则量和判断结构有限，先用
纯函数实现确定性分类与选规则；语义能力直接调用已有内部模型运行时。
未来有复杂规则语言需要时再评估成熟开源实现及许可证，当前不纳入第三方代码。

| 边界 | 职责与变更 |
| --- | --- |
| config | 校验 routing 配置、类型/规则引用、开关、版本；经 ConfigPlan 应用 |
| domain/protocol | 纯数据类型：TaskType、ModelRoutingRule、ModelRoutingDecision、ExecutionSelection；不引入网络、SDK 或持久化依赖 |
| scheduler | 纯关键词/规则函数；既有资源筛选保留；dispatch 显式接收冻结执行选择 |
| controller | 预览、分类调用、确认、原生查询、决策事务、幂等和权限 |
| llm-runtime | task_classifier 角色、受限调用、本次实际执行来源及用量元数据 |
| adapters | 按原生能力读取/校验/映射模型和 effort；按 session 固定选择 |
| web / Fleet | 设置、发布结果及确认、历史证据、已有 SSE 刷新 |

Controller service 已集中多条链路，新增分类/决策逻辑放在独立的就近模块，
service 仅编排；不把全部规则条件继续塞入 performDispatchTask。域类型及
ConfigPlan 不复制另一份 provider 规则，各层通过类型契约共享。

拟议接口（未实现）：

- `POST /api/model-routing/preview`：已登记项目、账号、标题/任务、草稿 revision、
  selectionMode、自动模式可选显式任务类型/手动模式完整选择 → 决策结果或
  needs-input、解释及版本。自动模式使用服务端当前 policy；混合识别会发起
  一次受限的内部分类调用。手动模式不调用分类模型，不接受缺失的执行参数。
- `POST /api/model-routing/test`：相同输入及可选配置草稿 → 标记为试算的解释；
  草稿试算须有现有配置编辑权限，返回值不是可派发决策。
- 扩展既有 `POST /api/tasks/:id/dispatch`，接收 decisionId、expectedInputRevision、
  acknowledgement（确认开启时）和既有幂等键；已有调用保持兼容。
  本地任务创建先沿用发布页的 canonical Task 流程，将输入摘要及 contract
  revision 绑定决策，再进入同一 dispatch，不另开绕过 READY 的入口。
- 设置读取/保存继续使用现有 ConfigPlan API，不新增直接写 routing.json 的接口。
- 任务/运行查询增加路由快照及事件投影；历史不再调用 LLM 重算原因。

纯预览依赖已解析的 repositoryId，不接受客户端任意执行目录。系统目录
选择器与项目登记、普通目录支持、原目录修改策略由本地发布功能解决。
本地发布入口在 canonical Task 来源中留下服务端登记的入口标识。该 Task
通过既有 dispatch API 启动也必须带有效选择记录：自动模式须有已匹配规则
的决策，手动模式须有完整显式选择。省略 decisionId 不能自动走旧兼容分支。
客户端传入 origin 或 confirmed 不具有入口识别权。
旧入口的兼容只适用于其真实服务端来源及已有调用契约。

向后兼容：旧配置缺 routing 时解析为关闭；可增加可选配置块并保留 schema
的版本约束，升级默认值必须有往返测试。旧 Run 缺决策记录显示「历史运行
未记录路由」，不根据当前规则补造。新发布页选择来源是 user / keyword-policy /
semantic-policy / hybrid-policy；手动采用账号默认候选可附记 user-selected-default。
旧入口的 account-default 来源保留兼容，不能作为自动模式的未匹配路径。
runtime 是另一个证据字段。

## 11. 任务与运行中的记录与费用

运行详情显示「当时为什么这样执行」：原始类型判断、关键词及语义依据、
胜出规则和优先级、policy 版本、是否降级/手动覆盖、确认方式、选定模型和
effort、执行端实际回报，以及与本次运行绑定的价格快照。

账号默认值、规则或内部分类模型之后变化不能修改这份记录。新的尝试或
reroute 各有自己的选择事实。原始任务在 canonical Task 保存；分析记录
存摘要和必要片段，遵守已有访问、脱敏及数据保留边界，不建立公开日志副本。

执行用量延续文档 06：输入/输出/缓存、真实消耗与倍率估算分别显示，保留
单位、范围和更新时间。模型路由不凭任务文字预估 token 数，发布前只有
当前费率/倍率，不能伪造任务总价。内部分类用量单列为「路由分析用量」。
CLI 费率和真实执行用量足够时才计算估算；不能把内部分类 API 的 token
按执行 harness 的倍率收费，也不把估算用作真实余额或资源阻塞依据。

## 12. 异常与用户处理

| 情况 | 结果与操作 |
| --- | --- |
| 路由关闭 | 仅手动模式，明确选定模型/effort 才可开始，无分类调用 |
| 无任务类型或无匹配规则 | NO_MATCHING_RULE / 未识别，提示手动指定模型及思考强度，阻止启动 |
| 分类歧义/关键词语义冲突 | 选择任务类型或手动模型；不开启猜测式执行 |
| 语义服务未配置/超时/输出无效 | 默认停止自动选择；配置允许时仅降级到唯一关键词结果 |
| 同级规则目标不同 | RULE_CONFLICT，展示规则并修正/手动指定 |
| 胜出规则模型消失/账号无权 | MODEL_UNAVAILABLE，不能退回其他规则 |
| 显式 effort 不支持或未验证 | REASONING_UNSUPPORTED，改选有效值或明确原生默认 |
| CLI 查询失败或返回明确过期数据 | 保留上次快照供查看，阻止该新启动，允许重试 |
| 输入/policy/有效目录或价格变化 | ROUTING_DECISION_STALE，更新展示后重新开始 |
| 需要确认但没有有效 acknowledgement | ROUTING_CONFIRMATION_REQUIRED，显示当前结果 |
| 输入过长 | CLASSIFICATION_INPUT_TOO_LARGE，修改分类说明或改模式，不截断任务 |
| 原生目录仅列出模型但未证明账号授权 | 展示访问权限未确认；显式开始仍可尝试，真实失败不换模型 |
| 资源/容量不满足 | 按现有状态处理，路由确认不能越过资源门槛 |
| 重复开始/网络丢失响应 | 返回原幂等 Run，不能重复启动 |

原生目录仅能返回内部缓存时，区分「已进行新的原生查询」与「上游实时性
未确认」，显示「CLI 缓存，实时性未确认」。路由严格要求发布前进行新原生
查询，不能用 Dispatcher 上次结果替代；明确过期数据不能执行。原生查询成功
且选择校验通过，但未提供价格或新鲜度证据时，分别显示「未提供」或「未确认」，
沿用目录设计的显式开始流程，不补造实时价格或账号授权证明。
